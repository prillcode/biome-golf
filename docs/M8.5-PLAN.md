# M8.5 - V1 Playability and Round UX Hardening

**Status:** Planned. Implementation has not started. Baseline: M8 closeout at
`b690e2f`, followed by the shot/ball hardening, solo/Ready Golf state separation,
and `0.2.7` release fixes. The current `0.2.8` no-course-selection work is a
prerequisite for this milestone.

M8.5 stabilizes the authored-course and round lifecycle before a new game mode
is introduced. It is deliberately a hardening and verification milestone, not a
feature expansion. The goal is to make solo play, Ready Golf, authored courses,
replay, withdrawal, and recovery consistently understandable and safe for
repeated play.

## Purpose

Ensure that a player can select any valid authored course, play it alone or in a
Ready Golf round, complete or abandon it, replay it, and recover from expected
interruptions without developer intervention.

Recent post-M8 fixes corrected several important seams:

- authored courses with more than three holes can complete without scorecard
  corruption or server crashes;
- solo course state no longer creates hidden Ready Golf state;
- stale, abandoned, and one-player round state is cleaned up consistently;
- sand shot behavior and Driver validation are explicit;
- a server restart no longer silently selects the retired M5 course.

M8.5 turns those fixes into explicit contracts, regression coverage, and manual
play evidence before M9 alternate modes are considered.

## Existing seams and required change

- `ActiveHoleService` owns the integration boundary between authored course
  selection, solo course state, Ready Golf state, hole sessions, and HUD
  snapshots.
- `ReadyGolfRound` owns shared participant lifecycle and completed-round replay
  or withdrawal behavior.
- `PlayerCourseState` owns ordered per-player course progress and scorecards.
- `HoleStatePayload` is the server-authoritative source for client HUD state,
  including no-course, active, missing-ball, complete, and round-complete
  phases.
- `GolfHoleCommands` exposes separate hole-scoped and round-scoped lifecycle
  commands.
- Authored course definitions and persistence are already delivered by M8;
  M8.5 must not replace them with a new course system.

Do not create a generic workflow framework, client-side gameplay state, a second
round implementation, or a new persistence layer. Repair and test the existing
seams.

## Locked gameplay contracts

### Course selection and startup

- Course selection remains runtime-only. After a server restart, no course is
  selected until an operator runs `/golf course select <id>`.
- A player receives a clear no-course-selected state and actionable feedback
  rather than a retired M5 fallback or a null-state failure.
- Only finalized, valid authored courses may be selected for play.
- Course selection, editing, deletion, and reset remain blocked while active play
  would make those operations unsafe.
- The existing deterministic M5 three-hole course remains a regression fixture,
  but it is not silently selected at startup.

### Solo and Ready Golf isolation

- Solo `/golf hole start` remains independent from Ready Golf state.
- Creating, joining, starting, leaving, or completing a Ready Golf round must not
  create or mutate hidden solo course state.
- Solo restart, abandon, progression, completion, and replay affect only the
  caller.
- Ready Golf restart, withdrawal, completion, and replay affect only the
  participants and balls covered by the relevant round contract.
- No cleanup operation may remove, move, score, or replace another golfer's
  assigned ball or course state.

### Command and HUD guidance

- During an active hole, `/golf hole restart` replays only the current hole.
- `/golf round leave` is the only exit action. It leaves a lobby, abandons solo
  play, withdraws from active Ready Golf, or exits a completed round.
- After a shared round completes, remaining participants use
  `/golf round restart` to replay Hole 1 together or `/golf round leave` to leave
  individually.
- The completed-round HUD must not advertise hole-scoped commands or the active
  round leave command as a valid completed-round action.
- HUD text must distinguish no course, practice, active hole, missing ball,
  completed hole, and completed round states without deriving authority or score
  on the client.
- Server rejection messages must identify the valid scope of the corrective
  command and must not claim that an unavailable transition succeeded.

### Recovery and lifecycle safety

- Missing assigned balls remain an explicit recoverable state and direct the
  player to the player-scoped restart path.
- Restart removes only stale state owned by the caller and creates a fresh
  authoritative ball after validation.
- Abandon and leave remove the caller's active session and ball without blocking
  remaining golfers.
- Disconnect and reconnect behavior preserves the existing M6/M7 contracts;
  M8.5 may clarify or test them but must not weaken server authority.
- A malformed course, unsupported dimension, missing transition position, or
  failed ball setup fails safely without partially advancing a round.

## Bounded slices

Each slice must pass its verification before the next begins. Stop and document
any required deviation from `docs/ARCHITECTURE.md`.

### S0 - Establish the post-M8 baseline

**Goal:** Make the current quick fixes a known, buildable baseline before adding
new hardening work.

**Deliverables:**

- Finish the current no-course-selected behavior and documentation updates.
- Confirm the JAR version policy for the local fix build and record the intended
  release version only when the quick fixes are ready to release.
- Reconcile `CHANGELOG.md`, `README.md`, and `docs/M8-CLOSEOUT.md` with the
  runtime behavior.
- Confirm the M8 authored-course workflow remains documented and selectable.

**Verification:** `./gradlew test`, `./gradlew build`, and `git diff --check`.

**Exit criteria:** A clean build represents the current post-M8 behavior, with no
  stale documentation claiming that the retired M5 course is selected after
  restart.

### S1 - Lifecycle contract and command/HUD regression coverage

**Goal:** Pin the intended distinction between hole-scoped and round-scoped
commands in automated tests.

**Deliverables:**

- Add focused tests for command registration or service routing where practical.
- Add service/domain coverage for solo start, solo restart, solo abandon, and
  solo replay.
- Add Ready Golf coverage for active leave, completed-round restart,
  completed-round leave, and remaining-participant isolation.
- Add tests for no course selected, invalid course selection, and valid authored
  course selection.
- Add tests proving `/golf round leave` performs the state-appropriate exit and
  removed exit commands are not registered or advertised.
- Add client-side HUD tests or a small presentation seam if needed to prevent
  regression from round commands back to hole commands. Do not move gameplay
  authority into the client to make this test easier.

**Verification:** `./gradlew test`.

**Exit criteria:** Automated tests pin all command scopes and lifecycle outcomes
  that were ambiguous or regressed after M8.

### S2 - Authored-course and arbitrary-length course regression

**Goal:** Prove that M8's generalized course model remains playable after the
  recent lifecycle fixes.

**Deliverables:**

- Test one-hole, three-hole, and greater-than-three-hole authored course flows
  through validation, selection, progression, final scoring, and replay.
- Test optional/unbounded hole bounds and bounded transition validation.
- Test persistence load/save, malformed data rejection, and runtime selection
  reset after server restart.
- Test course protection and cup/flag recovery at authored locations.
- Confirm no test relies on the retired implicit M5 startup selection.

**Verification:** `./gradlew test`, `./gradlew clean test build`.

**Exit criteria:** Valid authored courses of supported lengths complete with
  correct per-hole and cumulative scores, and invalid or stale definitions fail
  closed without corrupting the active course.

### S3 - Dedicated-server and Docker recovery verification

**Goal:** Prove that the lifecycle contracts survive the real server boundary.

**Deliverables:**

- Verify Loom dedicated-server startup with no client-only class leakage.
- Verify a clean server restart leaves no course selected and requires explicit
  operator selection.
- Build and sync one known JAR to Docker, recording artifact identity where
  practical.
- Verify authored course persistence across Docker restart.
- Exercise no-course, course selection, solo start, and Ready Golf start paths on
  the dedicated server.
- Verify server logs contain actionable rejection and cleanup messages without
  per-tick noise.

**Verification:**

- `./gradlew clean test build`
- Loom `runServer`
- `./scripts/dev-server-sync.sh`
- `./scripts/dev-server-up.sh`
- Docker health and startup-log checks

**Exit criteria:** The dedicated server boots cleanly, loads authored-course
  persistence, rejects invalid lifecycle transitions safely, and does not depend
  on client classes or a hidden default course.

### S4 - Manual solo and Ready Golf play acceptance

**Goal:** Validate the player-facing loop with actual Minecraft clients before
  introducing another game mode.

**Solo matrix:**

1. Restart the server and confirm the no-course-selected state.
2. Select a valid authored course and start solo play.
3. Complete a short authored course and verify per-hole and final totals.
4. Restart an active hole and confirm only the current hole resets.
5. Abandon solo play and confirm practice becomes available without stale state.
6. Replay the course and confirm Hole 1, zero current strokes, and fresh balls.
7. Exercise missing-ball recovery and a rejected shot after completion.

**Ready Golf matrix:**

1. Create, join, and start a shared authored-course round.
2. Confirm separate balls, HUD state, strokes, and scorecards.
3. Leave one player during active play and confirm the other player continues.
4. Complete the round and verify the HUD offers `/golf round restart` and
   `/golf round leave`.
5. Use round restart and confirm all remaining participants return to Hole 1.
6. Use round leave for one participant and confirm only that player exits.
7. Repeat with a disconnect/reconnect and missing-ball recovery where practical.

**Verification:** Two-client Docker/LAN testing whenever practical, with manual
results recorded in the closeout document.

**Exit criteria:** A player can complete, replay, leave, or recover from a solo
or Ready Golf authored-course attempt without developer intervention, and the
HUD/command guidance matches the valid action in every terminal state.

## Verification ladder

M8.5 is not complete merely because the code compiles. The highest applicable
verification rung must pass:

```text
unit tests
    -> Gradle clean test/build
    -> Loom client/server startup
    -> Docker dedicated-server boot
    -> manual solo play
    -> manual two-player Ready Golf play
    -> M8.5 closeout
```

## Risk register and stop conditions

| Risk | Mitigation / proof |
|---|---|
| A quick fix restores hidden solo/Ready Golf coupling | Keep separate state tests and repeat both start paths after every lifecycle change. |
| HUD advertises a command the server rejects | Test command scope against the authoritative service behavior; do not duplicate rules in the client. |
| Generalized authored courses regress the M5 fixture | Exercise one-, three-, and greater-than-three-hole courses and retain the M5 regression fixture. |
| Restart or cleanup affects another golfer | Require player UUID and assigned ball UUID ownership in tests and two-client play. |
| Server restart falls back to stale course state | Test no-selection startup in Loom and Docker, including persisted authored-course data. |
| Hardening expands into a new feature system | Keep wind, alternate modes, multiple tees, chip shots, and presentation polish out of this milestone. |

Stop and consult the user before implementation proceeds if:

- a fix requires weakening server authority or moving score/state decisions to
  the client;
- a lifecycle change requires a new persistence, matchmaking, or permissions
  system;
- authored-course validation or selection must be redesigned rather than fixed;
- a verification rung fails and cannot be repaired within the current slice; or
- the proposed work starts implementing M9 or another deferred feature.

## Non-goals

Do not implement Scramble, traditional turns, Match Play, Best Ball, wind,
advanced lies, cinematic camera, landing prediction, chip shots, multiple tee
boxes, expanded clubs, persistent statistics, leaderboards, matchmaking, public
server infrastructure, course sharing, a visual course editor, or a new course
generation system.

Do not add broad presentation polish unless it is required to make the lifecycle
state understandable or to fix a confirmed playability defect.

## Completion record to capture

At closeout, record:

- final commit and release/JAR version decision;
- final test count and focused lifecycle coverage;
- no-course startup and authored-course selection evidence;
- solo restart, abandon, replay, and missing-ball results;
- Ready Golf leave, completed-round restart, done, and isolation results;
- Loom client/server and Docker startup evidence;
- Docker persistence and JAR identity evidence where applicable;
- manual playtest findings and remaining accepted gaps;
- explicit recommendation to begin M9 or continue hardening.
