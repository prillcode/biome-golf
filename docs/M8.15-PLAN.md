# M8.15 Proposal — Golf, World, and Course Builder Modes

**Status: Approved and implemented.** Resolved 2026-09-30: Golf is **flight-only, not
literal Creative** (full inventory isolation avoided); the pale fence is
`minecraft:pale_oak_fence` with `minecraft:pale_oak_button`. **Resolved 2026-10:
Builder moved to true Creative for operators with the curated palette as an inventory
starter kit**, superseding the isolated Builder design detailed below for Builder;
Golf remains flight-only and the landscape protection still applies to everyone.
This is a follow-up product decision, not M9 alternate golf game modes. M8.13/M8.14
implementation scope is unchanged.

## Goal

Supported Java players golf in Creative (including flight) by default, and explicitly
switch to Survival/Peaceful for mining and building outside course landscapes. Course
builders also need a curated, replenishable palette (for example lime wool, green wool,
and moss carpet) without exporting free materials into Survival. These are player modes
in the same Minecraft world, not separate dimensions/worlds. Visitors retain their existing
Survival/Spectator experience.

## Findings

- Docker currently sets Survival/Peaceful, with `force-gamemode=false`. The mod does not
  set a supported Java golfer's game mode on solo or Ready Golf starts.
- `ActiveHoleService.leaveRound` intentionally returns to practice. It is not currently
  a world-play exit, and completed-round leave can teleport to world spawn.
- Commands and the browser/menu network actions converge on `ActiveHoleService`.
  Changing only command handlers would miss GUI actions and other round participants.
- Visitors use `/golf spectator` and `/golf spectator leave`; the latter returns them to
  Survival. These commands reject supported modded Java clients.
- Existing course protection is dimension-indexed and applies regardless of game mode
  or round membership. It protects break/place/TNT paths, not every vanilla mutation.
  Locked landscapes deny operators too; unlocked landscapes exempt operators.
- Read-only Docker inspection found River's Edge 18 (`re18`) has an **unlocked** landscape.
  No server settings, modes, inventories, or landscape locks were changed during research.
- PRD section 27 originally left Minecraft survival rules to the server. This bounded V1
  player-mode policy needs an explicit product/docs update before implementation.

## Recommended Player Contract

| Mode | Proposed experience | Purpose |
|---|---|---|
| Golf | Creative-style flight and damage protection; literal GameType decision pending | Practice, solo golf, Ready Golf, and flight around the course |
| World | Survival | Normal mining/building outside protected landscapes |
| Builder | Flight with an isolated, replenishable approved-material palette | Authorized terrain construction on a selected course |
| Visitor | Existing Survival/Spectator policy | Join the world or watch; cannot play golf |

Commands, registered on the server only:

- `/golf mode golf`: supported Java player enters Golf mode and can practice or browse.
  Does not silently start a scored round.
- `/golf mode world`: explicitly leaves their lobby/solo/shared attempt, cleans up their
  practice balls, and enters World mode. Feedback must warn that an unfinished attempt is
  abandoned; use a confirmation for an active attempt rather than silently destroying it.
- `/golf mode build <courseId>`: authorized builder enters the isolated construction
  loadout for the specified course; confirm leaving unfinished golf first.
- `/golf mode status`: explain the current mode, selected build course if applicable,
  and available switch.

Keep `/golf round leave` as "leave this round and return to golf practice". Do not give
it a second, ambiguous World-mode meaning. Offer the mode switch through chat initially;
a Golf Menu button can use the same server transition if included in the approved slice.

### Defaults and Lifecycle

- A supported Java player's first mode-managed join defaults to Golf. Persist an explicit
  World selection so reconnect does not unexpectedly take a miner back to Creative.
- Successful solo start, Ready Golf lobby create/join, and round replay select Golf mode.
  Failed actions must leave game mode and inventory unchanged.
- Apply Golf mode to every participating golfer through the shared service commit paths,
  including GUI actions, not only the coordinator/command caller.
- Completion and ordinary round leave retain Golf mode for scorecards/replay/practice.
- Returning to an existing round after disconnect must reconcile to Golf mode. A server
  restart still cancels runtime rounds as it does today; selected Golf mode then means
  practice, not fabricated round recovery.
- While in World mode, accidental B/right-click must not silently grant Creative. Golf
  commands can offer the explicit mode switch; intentional solo/lobby entry switches it.
- Keep the server-wide default Survival and `force-gamemode=false`; visitors and
  unsupported clients must never receive Creative via the Java Golf-mode path.
- Peaceful remains a server-wide difficulty, not a per-player mode setting.
- Switching out of flight must first find safe footing; do not remove flight midair.
  Respect existing round-leave travel and validate any new relocation before committing.

## Course Builder Refinement

The user clarified that meaningful Survival must coexist with freely available **selected**
course-building materials. Recommended refinement (superseded 2026-10 by the Creative
Builder decision below):

- Keep golf play separate from course construction. Golfers do not need a general Creative
  item catalogue; builders do need a curated material supply.
- **Approved 2026-10:** Builder uses literal Creative `instabuild` and the full item
  catalogue for operators, with the curated palette supplied as the inventory starter
  kit. This directly supports the author's workflow: trees and terrain clear in one
  click, materials never run out, and the perimeter can be authored after the holes
  exist.
- Start Builder permission at the existing operator/gamemaster authoring permission. A
  delegated builder role would be a separate, explicitly approved extension.
- **Superseded 2026-10:** the isolation model below (separate Builder inventory,
  export blocking, whitelisted placement, perimeter-scoped edits, per-builder lock
  exception) was replaced by **Creative Builder**: operators build with true Creative
  and the palette is only the starter kit. Creative items intentionally carry into
  World play; legacy World snapshots from the isolation era are restored once and
  retired. The authored landscape perimeter still protects courses from everyone,
  including the Creative Builder when locked.

### Editable Builder Palette (Requested Refinement)

Use a server-owned `config/minecraft_golf/builder_palette.json` with an explicit list of
registered item IDs. Operators can add/remove materials without a mod rebuild. Example:

```json
{
  "schemaVersion": 1,
  "items": [
    "minecraft:lime_wool",
    "minecraft:green_wool",
    "minecraft:moss_carpet",
    "minecraft:birch_fence",
    "minecraft:stone_button",
    "minecraft:oak_button"
  ]
}
```

The pale fence/button agreed during refinement are `minecraft:pale_oak_fence` and
`minecraft:pale_oak_button`.

- Load on startup; propose operator-only `/golf builder palette reload` for deliberate
  reloads. Validate the complete replacement first, and retain the last valid palette on
  malformed JSON or unknown IDs. Do not silently substitute an unknown item with air.
- Generate a documented default on first use. Bound the palette to one inventory slot
  per item (30 palette items + the 6-club Driver-through-Wedge set exactly fill the
  36-slot main inventory) and use the file as the Builder **starter kit**: one of each
  configured block plus the play-test clubs, applied on entry/reconnect and via
  `/golf builder restock`. In Creative mode stacks do not deplete, so no auto-refill is
  needed. File membership grants material access, not arbitrary item-component/NBT data.
  The default palette is a landscaping range of 30 items: sand, soil, common stone,
  logs, leaves, saplings, bushes, grass, ferns, and flowers, plus the pale-oak
  fence/button marker items.
- Since Builder is Creative, one-click breaking, free placement, and the full item
  catalogue are native Minecraft behavior; no erase hook or per-second sanitation runs.
- Removed items disappear from the starter kit on the next `/golf builder restock` after
  a successful reload; existing terrain is never erased by a palette change.
- Keep explicitly unsafe/unsupported item types rejected unless their handling is
  implemented and reviewed. Config edits cannot silently defeat course/material policy.
- Fence/button materials are decorative construction items. Buttons placed as tee
  markers do not replace `/golf hole tee <number>` metadata capture.
- Keep custom cup/flag assembly **command-managed**. `GolfBlocks` registers blocks, not
  inventory BlockItems; `/golf hole cup <number>` already records hole metadata and
  places the cup plus middle/top flag parts. They need not be in the material palette.
  Allow the authoring command workflow for an authorized Builder's selected course,
  respecting existing draft/finalized metadata rules and validated perimeter scope.
- Do not automatically allow a builder to move metadata on a finalized course: use the
  existing draft authoring workflow until a separately approved editing contract exists.

With this refinement, **flight-only Golf + curated Builder + normal World** is the
preferred lower-risk implementation. Literal Creative for Golf remains an open product
choice; it would additionally require the broader isolation described below. The curated
Builder inventory is still real state-management work, not a cosmetic inventory filter.

## Protection and Inventory Decision

**Recommendation: protected Golf play, not unrestricted Creative building.**

Actual Creative grants free items as well as flight. Course block protection alone does
not prevent Creative items from entering a Survival inventory, dropped items, containers,
or another player's inventory. Simply toggling `GameType` would not preserve meaningful
Survival play.

If actual Creative is retained as requested:

- Save the World inventory durably before entering Golf; use a separate golf loadout.
- Restore World items on exit without overwriting or duplicating them. Reconnect, respawn,
  restart, repeated switching, and interrupted transitions must be explicitly tested.
- Golf players must not export items through drops or containers, pick up mined loot, or
  freely edit terrain elsewhere while in Creative. Keep deliberate building/mining in
  World mode. Review relevant vanilla transfer and mutation paths before claiming this
  separation is secure; two inventories alone are insufficient.
- Published course landscapes should stay protected in BOTH modes. Recommend locking
  the live course perimeter after approval so operators playing golf are protected too;
  existing unlock/relock commands remain the explicit maintenance mechanism.
- Audit bucket/fluid, ignition, hoe/farmland, entity interaction, and other mutation paths
  relevant to the chosen Golf interaction policy. Current break/place/TNT guards are not
  a claim of comprehensive world protection.
- Do not change global course locks merely because one golfer enters/leaves Golf mode.

**Lower-complexity alternative:** Golf mode grants server-controlled flight and damage
protection without actual Creative inventory. This provides the main Creative golfing
benefits while sharing normal Survival items. It is a different product decision, not
something to substitute silently. Choose this if avoiding a real inventory-separation
subsystem is more important than literal Creative mode.

Do not implement an unrestricted Creative/Survival toggle and call it an economy-safe
World mode. On a trusted family server, unrestricted Creative may be consciously accepted,
but that tradeoff requires approval.

## Implementation Outline (After Approval)

1. Lock the three-mode contract, Builder palette/permission, and actual-Creative versus
   flight-only Golf choice; update PRD, architecture, milestone scope, and command guidance
   deliberately.
2. Add a small server-owned player-mode service with Minecraft-native persistence, pure
   transition-policy tests, safe flight exit, and explicit visitor gating.
3. Hook successful shared lifecycle commits and reconnect/respawn into the service;
   implement server commands, feedback, and any approved menu action.
4. For actual Creative, implement and verify durable World-loadout preservation and
   Golf-mode transfer/edit restrictions before enabling the default.
5. Implement scoped Builder editing and a curated, isolated loadout if included in the
   approved slice. Audit/test protected course edits for golfers, World players, builders,
   and operators. Any new Mixin or larger protection system must be justified before
   proceeding.
6. Update help coverage, docs, and changelog; run the full verification ladder and deploy
   only with approval.

## Verification / Done Conditions

- Solo and every Ready Golf participant receive the chosen Golf abilities through both
  commands and GUI; failure, replay, completion, and leave semantics stay deterministic.
- World switch cleans up only the requesting golfer, unblocks the shared round correctly,
  and does not abandon an unfinished attempt without informed confirmation.
- World mining/building works outside protected terrain but not inside it; operator
  protection and deliberate maintenance are verified separately.
- Inventory/flight state cannot be lost, duplicated, exported, or stranded on switches,
  reconnect, death/respawn, dimension change, or server restart under the selected design.
- Builder palette placement/refills work only within the authorized selected course;
  inventory export, out-of-perimeter edits, unapproved items, course deletion, and revoked
  permission cannot leak Builder privileges or items into World play.
- Unsupported clients remain visitors and cannot invoke Java Golf/Builder privileges.
- Tests/build, Loom client/server, Docker health/JAR identity, authenticated-client mode
  transitions, and two-player gameplay/protection checks pass. No completion claim from
  compilation or startup alone.
