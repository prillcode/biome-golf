# M8.5 Ready Golf Lobby and Practice UX

**Status:** Superseded as a standalone plan. The implemented browser/lobby/menu work is
part of the committed baseline through `f65ca05`; concurrent-lobby corrections and any
remaining relevant acceptance are folded into the current `docs/M8.6-PLAN.md`. Do not
execute this plan independently.

**Purpose:** Define the implementation for replacing the current no-course-selected
practice HUD with a player-facing course browser and Ready Golf lobby flow.

## Requested Player Experience

When a player is not in a round and no course is selected, the HUD currently says
`No course selected` and tells the player to ask an operator to select a course.
The requested experience is:

1. Present this state as `Practice Mode`.
2. Show a nearby `Play a Round` action.
3. Open a modal listing finalized courses currently available on the server.
4. Allow the player to cancel and return to Practice Mode.
5. If the player chooses a course with no active round, create a Ready Golf round
   for that course.
6. If another player already created an active round for that same course, offer
   `Join` immediately.
7. After creation or joining, replace the practice HUD with lobby status such as
   `[n] of 4 players ready`.
8. Show `Start Round` to the player who created/coordinated the lobby.
9. Show `Leave` to a participant who withdraws before the round starts.
10. Start the round through the existing server-authoritative Ready Golf lifecycle.

The existing chat commands remain valid fallbacks. The new UI must not move course,
round, participant, or permission authority to the client.

The contextual Golf Menu is the M8.6 follow-up entry point. Automatic hot-zone or
clubhouse detection is intentionally deferred; if desired later, it can offer the
same menu from a server-validated course-area interaction without adding another
client-authoritative shortcut.

## Current Constraints

- `/golf course list` and `/golf course select` are operator-gated.
- `/golf round create` currently uses the server's globally selected course and has
  no course-ID argument.
- `/golf round join` joins the one active Ready Golf lobby and has no course-ID
  argument.
- Only one Ready Golf round exists per server.
- A Ready Golf lobby currently has no separate ready-toggle state. Joined active
  participants are the ready count, and only the coordinator can start.
- Finalized authored courses are already persisted by `AuthoredCourseService` and
  exposed by `AuthoredCourseStore.finalizedCourses()`.
- `ActiveHoleService` owns course selection, Ready Golf lifecycle, and server
  integration.
- `HoleStatePayload` and the existing typed networking classes establish the
  server-to-client presentation pattern.
- Client-only code must remain under `src/client/java/`.
- No new persistence system, alternate game mode, or M9 work is in scope.

## Recommended Design

Do not have the client inject `/golf ...` chat commands. Add purpose-specific typed
payloads whose server handlers invoke the same authoritative service operations as
the commands. This avoids command text parsing, preserves validation, and makes
the course ID explicit.

The chat commands remain available for operators, debugging, and fallback use.

### Course selection semantics

Course selection for a round should be round-scoped, not global runtime course
selection. The UI should not call the operator-only `/golf course select` command.

Recommended compatibility behavior:

- Keep `/golf round create` using the existing globally selected course.
- Add an optional `/golf round create <courseId>` fallback if useful for chat.
- Add a service method that creates a round directly from a finalized course ID.
- Do not change the global selected course merely because a player browses or
  creates a round.

### Active-round semantics

Because only one Ready Golf round exists server-wide:

- If no active lobby/round exists, a player may create a round for any finalized
  course that is valid for the current server/world rules.
- If an active lobby exists for the selected course, a player may join it.
- If an active lobby exists for a different course, the UI must show that another
  course is currently in use and reject creation/join safely.
- A completed round is not joinable; the existing completed-round replay/done
  behavior remains unchanged.

### Ready count semantics

Use the existing lobby model for this slice. `n of 4 players ready` means `n of 4
players currently joined and active in the lobby`. Do not add an independent ready
toggle unless product direction changes; that would require a new state machine and
new command semantics.

## Implementation Slices

### S1 - Server course browser and typed requests

**Goal:** Make finalized courses and lobby actions available through authoritative
network contracts.

**Likely files:**

- `src/main/java/com/prillcode/minecraftgolf/course/AuthoredCourseStore.java`
- `src/main/java/com/prillcode/minecraftgolf/server/AuthoredCourseService.java`
- `src/main/java/com/prillcode/minecraftgolf/server/ActiveHoleService.java`
- `src/main/java/com/prillcode/minecraftgolf/round/ReadyGolfRound.java`
- `src/main/java/com/prillcode/minecraftgolf/net/`
- `src/main/java/com/prillcode/minecraftgolf/MinecraftGolf.java`

**Work:**

- Add a server-to-client finalized-course-list payload containing only display-safe
  data: ID, display name, hole count, and total par.
- Add a serverbound course-browser request or a small request payload for opening
  the list.
- Add serverbound Ready Golf lobby actions for create-by-course, join, start, and
  leave, or keep create/join/start/leave as one typed action payload with bounded
  arguments.
- Resolve course IDs through `AuthoredCourseStore.finalizedCourse`.
- Add a create-by-course service path without mutating global course selection.
- Enforce finalized-course validation, one-active-round rules, capacity, active
  participant status, and coordinator-only start on the server.
- Preserve `/golf round leave` for active-lobby/active-round withdrawal.

**Done when:** The server can safely list finalized courses and perform each UI
action without trusting client-supplied course, participant, or lifecycle outcomes.

### S2 - Server-authoritative lobby state synchronization

**Goal:** Keep every connected participant's lobby HUD current.

**Likely files:**

- `src/main/java/com/prillcode/minecraftgolf/net/`
- `src/main/java/com/prillcode/minecraftgolf/server/ActiveHoleService.java`
- `src/main/java/com/prillcode/minecraftgolf/round/ReadyGolfRound.java`

**Work:**

- Add a clientbound lobby-state payload containing:
  - lobby/round phase,
  - course ID and display name,
  - active participant count,
  - maximum participant count,
  - whether the local player is participating,
  - whether the local player is coordinator,
  - and whether the lobby is startable.
- Broadcast state after create, join, leave, disconnect, reconnect where relevant,
  start, and rejected/stale transitions that could leave the client outdated.
- Clear lobby state when the round starts or the local player leaves.
- Do not duplicate Ready Golf state in a client-authoritative model; the client
  stores only the latest display payload.

**Done when:** Two or more clients see the same authoritative lobby membership and
coordinator/start availability after each lifecycle action.

### S3 - Practice Mode and course browser UI

**Goal:** Replace the dead-end no-course guidance with a usable course entry point.

**Likely files:**

- `src/client/java/com/prillcode/minecraftgolf/client/hole/HoleHud.java`
- `src/client/java/com/prillcode/minecraftgolf/client/hole/`
- `src/client/java/com/prillcode/minecraftgolf/client/MinecraftGolfClient.java`

**Work:**

- Change the no-course HUD presentation to `Practice Mode`.
- Add a `Play a Round` button or equivalent client-only action.
- Add a modal listing finalized courses received from the server.
- Show course display name, ID where useful, hole count, and total par.
- Show `Play`/`Create Round` when no compatible active round exists.
- Show `Join` when the active round is for that course.
- Show a clear unavailable state when another course already has the active round.
- Add `Cancel` that closes the modal without changing practice state.
- Handle an empty course list and server rejection without leaving a stuck modal.

**Done when:** A player can enter and cancel the course browser without affecting
practice mode, and can initiate the correct server request for a displayed course.

### S4 - Lobby HUD and lifecycle actions

**Goal:** Present the Ready Golf lobby state and expose its valid actions.

**Likely files:**

- `src/client/java/com/prillcode/minecraftgolf/client/hole/HoleHud.java`
- `src/client/java/com/prillcode/minecraftgolf/client/hole/`
- `src/client/java/com/prillcode/minecraftgolf/client/MinecraftGolfClient.java`

**Work:**

- Add a lobby HUD state/cache driven only by the server payload.
- Render selected course and `[n] of 4 players ready` or equivalent wording.
- Render `Start Round` only when the server says the local player is coordinator and
  the lobby is startable.
- Render `Leave` for active lobby participants.
- Send typed requests and close/retain screens based on server responses.
- Transition cleanly from lobby state to the existing active-hole HUD on start.
- Preserve completed-round replay through `/golf round restart`; use the unified
  `/golf round leave` action to exit after completion.

**Done when:** The client cannot present a start or leave action in an invalid
state, and the UI follows server updates rather than predicting lifecycle success.

### S5 - Tests, documentation, and verification

**Goal:** Prove the feature without weakening M8.5 contracts.

**Automated coverage:**

- Finalized course list excludes drafts.
- Course-list payload round-trips and limits data to display-safe fields.
- Create-by-course rejects missing, draft, malformed, or incompatible courses.
- Same-course join succeeds.
- Different-course join/create is rejected while another round is active.
- Four-player capacity is enforced.
- Only the coordinator can start.
- Active-lobby leave removes only the caller.
- Lobby state payload round-trips with coordinator and participant flags.
- No-course/practice state remains available outside a round.
- Starting a Ready Golf round does not create solo course state.

**Verification ladder:**

```text
./gradlew test
./gradlew clean test build
no net.minecraft.client imports under src/main
./gradlew runClient
./gradlew runServer
./scripts/dev-server-sync.sh
./scripts/dev-server-restart.sh
Docker health and startup-log checks
manual solo lobby test
manual two-player create/join/start/leave test
```

**Manual acceptance:**

1. Restart the server with no selected course.
2. Confirm the HUD says `Practice Mode` and still permits practice shots.
3. Open `Play a Round`, inspect finalized courses, and cancel.
4. Create a lobby for a selected course.
5. Connect a second client and join the same course.
6. Confirm both clients see the same participant count.
7. Confirm only the coordinator sees `Start Round`.
8. Have the second player leave and confirm the count updates without ending the
   lobby for the coordinator.
9. Rejoin, start the round, and confirm the existing Ready Golf hole flow begins.
10. Confirm a different-course create request is rejected while the lobby exists.
11. Confirm a full four-player lobby rejects a fifth participant.
12. Confirm active withdrawal uses `Leave` and completed-round withdrawal remains
    `/golf round leave`.

## Concerns and Counter-Proposals

### Global course selection

The current course-selection command changes a global runtime selection and is
operator-only. Reusing it from the UI would create permission and multiplayer race
problems. The recommended counter-proposal is a round-scoped course ID resolved by
the server, while preserving global selection for existing command fallback and
solo workflows.

### One active round per server

The requested “active round for that same course” wording implies multiple rounds
could exist. The current architecture supports only one. This plan keeps one active
round and clearly rejects other-course creation. Supporting concurrent rounds would
be a larger round-manager redesign and is out of scope.

### Ready versus joined

There is no current ready toggle. The plan treats joined active lobby members as
ready. If explicit readiness is desired later, add it as a separate focused feature
rather than silently expanding this implementation.

### Command invocation from a client

Sending literal chat commands from a screen is fragile and makes course arguments,
permissions, and error handling less clear. Typed serverbound intent is the safer
equivalent. The existing commands remain fallback interfaces.

### Course visibility and privacy

The modal will show all finalized courses in the server's authored-course store.
If course visibility or per-player permissions are later needed, add an explicit
server-side visibility policy; do not filter based on client input.

## Scope Guardrails

Do not implement:

- multiple simultaneous Ready Golf rounds;
- a separate ready-toggle state machine;
- persistent lobby state;
- matchmaking or public-server infrastructure;
- a visual course editor;
- alternate game modes or M9 work;
- client-side score, participant, course validity, or lifecycle authority.

## Final Success Criteria

The feature is complete when a player can remain in Practice Mode with no course
selected, open a server-provided list of finalized courses, create or join the
correct Ready Golf lobby, see authoritative participant/coordinator state, start or
leave using valid actions, and enter the existing server-authoritative round flow.

The existing chat commands, solo flow, course authoring, completed-round replay,
completed-round leave behavior, and dedicated-server compatibility must continue to
work unchanged.
