# M8.7 - Shot Variety and Trajectory Control

**Status:** Planned. M8.6 is complete; M9 remains deferred until this shot-variety
work is accepted or deliberately rescheduled.

M8.7 adds intentional trajectory choices without changing golf scoring, round lifecycle,
or the server-authoritative shot model. The existing Standard shot remains the default.

## Purpose

Add three useful shot types:

- **Chip:** for mid irons, short irons, and wedges; lower launch, softer landing, and
  more rollout.
- **Stinger:** for long irons, fairway woods, and drivers; lower flight, more forward
  momentum, and useful clearance beneath low-hanging terrain.
- **Flop:** for short irons and wedges; higher trajectory, shorter relative distance,
  and a soft landing with limited rollout.

This milestone is a shot-mechanics extension, not an alternate scoring mode.

M8.7 also adds a short-distance tap-in convenience action for a stationary ball near
the cup. It is a normal golf stroke, not a free hole completion.

## Keybind Decision

Use configurable keybind `C` as a contextual shot-cycle key:

- Driver, fairway wood, and long iron cycle Standard <-> **Stinger**.
- Mid iron cycles Standard <-> **Chip**.
- Short iron and wedge cycle Standard -> **Chip** -> **Flop** -> Standard.
- Putter remains Standard-only.

The swing HUD shows the selected mode, for example `Shot: Standard`, `Shot: Chip`,
`Shot: Stinger`, or `Shot: Flop`. The key is configurable so players can rebind it if
`C` conflicts with another client control. `L` remains a reasonable future/default
rebind for “low shot,” but `C` better describes the contextual shot-cycle action.

Tap-in reuses the existing configurable `B` keybind contextually and shows an on-screen
prompt when the server reports that the player is eligible. While a tap-in is available,
`B` invokes Tap-In. Outside an active eligible hole, `B` retains its existing practice
ball behavior. A clickable server-chat prompt and `/golf tapin` remain fallbacks for
clients that do not use the custom prompt or keybind.

## Locked Contracts

- The client sends shot intent, including the requested shot type; it never sends a
  resulting trajectory, landing point, distance, or score.
- The server validates the requested type against the held club before launching.
- Invalid combinations are rejected or normalized to Standard without consuming a
  scoring shot.
- Standard behavior remains unchanged for clients or payloads that do not request an
  alternate shot type.
- Accepted-shot counting, penalties, Pick Up, hole completion, and scorecards do not
  change based on shot type.
- Shot type is per-shot intent and does not become hidden server gameplay state after
  launch.
- Solo and Ready Golf use the same resolution and validation path.
- Tap-in eligibility is server-authoritative and requires the player's active resting
  ball to be within two blocks of the current cup. The exact boundary must be defined
  consistently, preferably using horizontal center-to-cup distance. (The boundary was
  widened from one block to two blocks in `0.5.1` after playtest.)
- An accepted tap-in increments accepted shots and total strokes by exactly one, then
  completes the hole through the same authoritative completion path as a ball entering
  the cup. It must never complete a hole for free.
- Tap-in is unavailable for a moving, missing, unowned/other-player, already-complete,
  or out-of-range ball. Repeated requests after completion are harmless rejections.

## Allowed Shot Matrix

| Held club | Standard | Controlled result |
|---|---:|---|
| Driver | Yes | Stinger |
| Fairway Wood | Yes | Stinger |
| Long Iron | Yes | Stinger |
| Mid Iron | Yes | Chip |
| Short Iron | Yes | Chip, Flop |
| Wedge | Yes | Chip, Flop |
| Putter | Yes | Unavailable; use Standard |

The matrix is server-owned and represented by tests rather than inferred only from
client UI labels.

## Tap-In Contract

- The server publishes or otherwise exposes a display-safe `tapInAvailable` state for
  the player's own active hole. The optional client prompt may only appear from this
  authoritative state.
- The prompt should communicate that the action counts as one stroke, for example:
  `Tap in (+1 stroke)`.
- The keybind and clickable prompt invoke the same server operation; neither client
  path may directly mutate the ball, hole, stroke count, or completion state.
- `/golf tapin` is the command fallback and uses the same validation/service method.
- Tap-in completion must fan out the same hole-complete, barrier, HUD, scorecard, and
  Ready Golf behavior as physical cup entry.

## Technical Direction

The current architecture already has the required extension seams:

- `ShotResolver` owns deterministic launch-vector calculation.
- `ShotPhysicsProfile` carries per-shot landing retention and rolling behavior.
- `BallPhysics` separately handles airborne motion, impact, and rolling friction.
- `ShotService` is the single server-side validation and launch authority.

Add a small Minecraft-free shot-type/profile model rather than duplicating shot
resolution. Chip, Stinger, and Flop profiles should independently tune vertical launch,
horizontal launch retention, landing retention, and rolling friction. Lowering or
raising launch height alone is insufficient: rollout also requires controlling forward
speed after impact and rolling friction. Existing surface behavior, bunker penalties,
water recovery, and collision rules remain active.

If the shot request schema changes, version the payload identifier, for example from
`shot_request` to `shot_request_v2`, and keep validation defensive against stale or
malformed clients.

## Bounded Slices

Each slice must pass its verification before the next begins. Stop and document any
required deviation from `docs/ARCHITECTURE.md`.

### S0 - Baseline and Shot Contracts

- Record the current test/build and JAR baseline.
- Add a Minecraft-free shot-type model and allowed-club matrix.
- Define deterministic Standard, Chip, Stinger, and Flop profile expectations without
  prematurely locking final tuning constants.
- Verify with `./gradlew test` and existing Standard shot regression tests.

### S1 - Server Resolution and Payload Evolution

- Add shot type to the finalized shot intent payload, versioning the identifier if the
  wire schema changes.
- Validate held club, requested type, legal aim, power, accuracy, and launch speed on
  the server.
- Route all shot types through one `ShotService`/`ShotResolver` path.
- Preserve scoring and ownership semantics exactly.
- Add payload round-trip, invalid-combination, stale/default behavior, and service tests.

### S2 - Contextual Client Selection

- Add configurable `C` keybind to cycle the legal shot choices for the held club.
- Resolve the visible controlled label from the held club without trusting the client as
  gameplay authority.
- Show the selected shot in the swing HUD and make unavailable Putter behavior clear.
- Preserve the existing three-click meter and post-shot camera flow.
- Verify through client compilation, code-path inspection, Loom startup, and manual use.

### S2.5 - Server-Authoritative Tap-In

- Add one shared tap-in service operation and `/golf tapin` command.
- Define and test the two-block eligibility boundary, active-ball ownership, resting
  state, current-hole state, and idempotent rejection cases.
- Reuse the existing accepted-shot and hole-out/completion path rather than creating a
  second completion state machine.
- Publish eligibility through the appropriate versioned hole-state/prompt projection.
- Reuse the configurable `B` keybind contextually: Tap-In when eligible, practice ball
  outside an active eligible hole. Add the active-only prompt, clickable chat fallback,
  and explicit `+1 stroke` wording.
- Verify that solo and Ready Golf barriers, scorecards, penalties, reconnect, and replay
  remain unchanged apart from the added stroke.

### S3 - Trajectory and Rollout Calibration

- Chip is lower than Standard for the same club/power, lands with more forward speed,
  and rolls farther on normal fairway/green surfaces.
- Stinger has a materially lower apex than Standard for the same club/power, retains
  forward speed, and can pass under tested low canopy when geometry permits.
- Flop has a materially higher apex than Standard for the same club/power, carries less
  relative distance, lands softly, and has limited rollout on normal fairway/green
  surfaces.
- No shot type bypasses max launch speed, collision, surface, hazard, or stop-speed rules.
- Add deterministic `ShotResolver`/`BallPhysics` tests, then calibrate in Loom/Docker on
  fairway, rough, green, bunker, water, and low-overhead terrain.

### S4 - Integrated Playtest and Closeout

The manual matrix must cover Standard preservation, every allowed Chip, Stinger, and Flop
club, invalid combinations, rollout, low-terrain collision, solo/Ready Golf isolation,
tap-in at exactly inside/outside the two-block boundary, the contextual `B` key and prompt paths,
penalties, Pick Up, completion, replay, reconnect, and scorecards.

Exit evidence consists of automated tests, Loom client/server startup, Docker health,
installed-client deployment, family/LAN playtest, and `docs/M8.7-CLOSEOUT.md`.

## Non-Goals

- Scramble, Match Play, Best Ball, or any alternate scoring mode.
- Wind, advanced lies, spin control, shot shaping, or a landing predictor.
- Automatic terrain-aware shot selection or tree avoidance.
- New clubs, multiple tee boxes, course authoring, or course persistence.
- Client-authored outcomes or a second physics/entity path.
- Changes to Ready Golf barriers, round membership, scoring rules, or ball ownership.
- Full unmodified-client support for custom balls, clubs, camera, or swing controls.

## Exit Criteria

M8.7 is complete when:

1. Standard, Chip, Stinger, and Flop are server-authoritative and validated by club.
2. Chip is available for mid iron, short iron, and wedge clubs with lower flight and
   useful rollout.
3. Stinger is available for long iron, fairway wood, and driver with lower flight and
   useful rollout.
4. Flop is available for short iron and wedge clubs with higher flight and shorter
   relative distance.
5. `C` cycles the legal contextual shot choices and the HUD communicates the active mode.
6. Tap-in is available within the server-defined two-block boundary, is exposed through
   the prompt/`B`/command paths, and adds exactly one stroke before hole completion.
7. Invalid combinations cannot launch an unauthorized alternate trajectory, and invalid
   tap-in requests cannot complete a hole.
8. Existing scoring, round isolation, collision, hazard, reconnect, and scorecard
   behavior remains intact.
9. Automated, Loom, Docker, installed-client, and family/LAN verification passes.
10. M8.7 closeout records tuning decisions, residual limitations, and the final artifact.
