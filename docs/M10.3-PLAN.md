# M10.3 — Tier 1 Cross-Play (Java-Safe)

**Status:** Tier 1 implemented (2026-09). Code, unit tests (`./gradlew test`), `./gradlew build`,
and the Docker/Geyser dev-server sync + restart are verified with matching JAR hashes and a
healthy container. The final acceptance step — a real two-client (modded Java + Bedrock) round
— is a manual playtest that remains pending.

## Purpose

Let Bedrock (via Geyser) and vanilla-Java players join the same server-authoritative
rounds and compete side-by-side, while the modded Fabric Java client is left **unchanged**.

Tier 1 deliberately accepts that non-mod clients see different (simpler) visuals. It does
**not** attempt Bedrock visual parity, a Bedrock resource pack, or camera parity. Those are
Tier 2 and are tracked as separate research at the end of this document.

## Why this is safe now

The simulation is already client-agnostic: physics, validation, scoring, rounds, and course
state are server-owned, and `ShotService` is the single mutation point. The only client
discriminator needed is already in the tree:

```java
ServerPlayNetworking.canSend(player, HoleStatePayload.TYPE)
```

This is true only for modded Java clients. Every Tier 1 fallback is gated on
`!canSend(...)`, so the modded HUD, payloads, three-click meter, custom ball renderer,
custom cup/flag blocks, and follow camera are untouched.

## Current baseline (what already works)

- **Connection.** Touched vanilla registries are marked `RegistryAttribute.OPTIONAL`, so
  unmodded clients connect. Geyser + Floodgate run via the dev-server overlay.
- **Clubs (dual).** Modded clients get the custom items; non-mod clients get distinct
  vanilla items with a display name and `custom_data` tag. `GolfItems.clubOf` recognises both.
- **Input.** `HeldShotService` (hold right-click → release → `ShotService`) plus the
  `/golf swing [power] [accuracy] [shotType]` command floor.
- **Ball.** `GolfBallEntity` mirrors itself with a vanilla item entity.
- **Camera.** `BallCameraService` exists but is shaky; see S2.
- **Gaps.** Non-mod clients get no hole/par/strokes/distance HUD and no scorecard
  (`RoundScorecardNetworking` drops it), the cup/flag are invisible, and the ball mirror
  currently spawns for **every** ball, so modded Java sees it too.

## Invariants

- **Server authority.** Clients send intent only; no outcome is ever client-supplied.
- **No client leakage.** `src/main/java` imports no `net.minecraft.client`.
- **Core stays Minecraft-free.** `ball/`, `club/`, `golf/`, `round/`, `hole/`, `course/`,
  `config/`, `surface/` keep zero `net.minecraft` imports.
- **Modded Java unchanged.** Payloads, `HoleHud`, `SwingHud`/three-click meter,
  `PostShotCamera`, the custom ball renderer, and the custom cup/flag blocks behave exactly
  as before. New fallbacks are additive and gated on `!canSend`.
- **No Mixins, no Hydraulic dependency.**

## Slices

### S1 — Ball mirror fix (Java regression; do first)

The vanilla mirror is spawned unconditionally in `GolfBallEntity.tickVisual`, so modded Java
sees a snowball alongside the custom ball. Fix by mirroring only while a client-light
player actually needs it.

- Decide a keep-alive condition: simplest is **"at least one non-mod player is online"**;
  a tighter version is "a non-mod player is within tracking range of the ball."
- Spawn when the condition becomes true; despawn (`discard`) when it becomes false.
- Keep the custom ball entity and its renderer authoritative and unchanged.
- Acceptance: modded Java sees only the golf ball; a non-mod client reliably sees the mirror.

### S2 — No server-side follow camera in Tier 1

The `SetCamera` spectate of the 20 Hz mirror is subjectively shaky and was the main reason
M10 was shelved. Tier 1 uses the ordinary first/third-person view instead.

- Remove the `BallCameraService.followShot(...)` call from `ShotService.attempt` (the class
  can stay dormant for possible Tier 2 work).
- Bedrock players watch the ball from their normal camera. Short shots are fine; drives are
  watched from the tee, which is acceptable and stable.
- Java is unaffected (it never used the server camera).

### S3 — Presentation fallbacks for non-mod clients

Mirror the existing server state into vanilla channels, gated to `!canSend`. Prefer
channels that are naturally per-player.

| Information | Channel | Notes |
|---|---|---|
| Hole / par / strokes / score-to-par | Action bar, then chat | `HoleScoringDisplay` already produces text |
| Distance to cup | Action bar on shot/rest | `HoleStatePayload.distanceToCupBlocks` already exists server-side |
| Shot power while charging | Boss bar | Drives from `HeldShotService` hold progress |
| HUD "current hole" panel | Boss bar / action bar | Per-player, easy |
| Final scorecard | Chat | Fallback where the payload is dropped today |
| Sidebar source list | Scoreboard (investigate) | Per-player display may need a manual packet; action bar/chat are the safe fallback |

- Do **not** change `HoleStateNetworking.send` or any payload shape.
- Chat text is per-player and cheap; boss/action bar are per-player by construction.

### S4 — Hole visibility without a physical cup

The custom cup/flag blocks are invisible to non-mod clients. Tier 1 does **not** place a
different block and does **not** change the Java visuals.

- Give non-mod clients the hole bearing via the S3 distance readout (and optionally a
  short "flag is X blocks away" action-bar line on rest).
- If that proves insufficient in the playtest, the follow-up is a non-block waypoint
  (boss bar/action bar), still gated and Java-safe.
- Explicitly rejected for Tier 1: replacing the custom blocks with vanilla markers (that is
  the change we already reverted because it degraded Java).

### S5 — Input hardening

- Verify held-use end-to-end with a real Bedrock client (Geyser sends `RELEASE_USE_ITEM`;
  confirm hold/release feel and that a quick tap still launches).
- Keep `/golf swing` as the guaranteed floor and the test seam.
- Optional refinement: measure hold duration on wall-clock rather than server ticks so tick
  lag does not distort power.
- Do not add a Bedrock-only accuracy mechanic in Tier 1; note the Java/Bedrock timing
  asymmetry as a known, accepted difference.

## Verification

Ladder, in order:

1. `./gradlew test` — add pure unit tests for any new presentation/formatting helpers.
2. `./gradlew build`.
3. `./scripts/dev-server-sync.sh` + Geyser overlay restart; confirm JAR hash match and a
   healthy container.
4. **Two-client round:** a modded Java client and a Bedrock client complete the same hole
   and round together. Check:
   - Java: no snowball, unchanged HUD/camera, custom cup/flag.
   - Bedrock: can take shots, sees hole/par/strokes/distance, sees the final scorecard.
   - Both: identical strokes/score from the server.

## Exit criteria

- A modded Java player and a Bedrock player complete the same round side-by-side with
  consistent server-authoritative scores.
- The modded Java experience is demonstrably unchanged (no new entities/visuals on Java,
  HUD and camera as before).
- No Bedrock acceptance is claimed beyond "plays and is scored correctly"; visual parity is
  explicitly out of scope.

## Implementation notes (Tier 1)

Recorded when the slice was implemented; kept for future maintainers.

- **S1 ball mirror.** `GolfBallEntity.tickVisual` now spawns/keeps the vanilla snowball proxy
  only while at least one client-light player (`!canSend(HoleStatePayload)`) is in the same
  dimension and within 64 blocks; otherwise it discards the proxy. Per-player entity hiding is
  not a vanilla primitive, so a *mixed* Java + Bedrock session within range may still show the
  proxy to Java. The normal all-modded-Java world shows only the custom ball, which is the
  acceptance target.
- **S2 camera.** The `BallCameraService.instance().followShot(...)` call was removed from
  `ShotService.attempt`; the class and its `SetCamera` machinery stay dormant for Tier 2.
- **S3 presentation (decision: action bar + boss bar + chat, no scoreboard).** The per-player
  sidebar would need a manual display packet; the lower-risk naturally per-player channels were
  chosen. A new `server/ClientLightPresentation` mirrors snapshots into the vanilla action bar,
  and `net/RoundScorecardText` renders the final scorecard to chat when
  `RoundScorecardNetworking` would otherwise drop the payload. Held-use charge power drives a
  per-player `ServerBossEvent` in `HeldShotService`. All paths are gated on
  `!canSend(HoleStatePayload)`; no payload shape, `HoleStateNetworking`, or modded HUD changed.
- **S4 hole visibility.** Delivered by the S3 action-bar distance readout ("cup N blocks"); no
  different blocks are placed and the M4 custom cup/flag are untouched.
- **S5 input.** Held-use and `/golf swing` are unchanged apart from the additive charge bar;
  the wall-clock timing refinement was deliberately not taken (out of Tier 1).

## Risks / open questions

- **Scoreboard per-player display.** Vanilla scoreboards are global server-side; showing a
  sidebar only to non-mod players would require sending the display packet manually. S3 chose
  the lower-risk action bar/boss bar/chat channels instead.
- **Geyser translation** of boss bar and any per-player display packet must be confirmed on
  the pinned Geyser build.
- **Cup invisibility** may make aiming harder than expected; S4 is the escape hatch.
- **Input asymmetry.** Java's meter rewards accuracy timing; held-use uses a fixed lane and
  is more lag-sensitive. Accepted for Tier 1.
- **Mirror visibility.** Entities are tracked distance-based for everyone; per-player hiding
  is not a vanilla primitive, so S1 uses an online-based keep-alive instead.

## Non-goals (Tier 1)

- Bedrock resource pack, custom Bedrock models, or custom block/entity rendering.
- Camera parity or camera smoothing.
- A Bedrock-only accuracy mechanic.
- Console Bedrock; Mixins; Hydraulic; marketplace/matchmaking; Gradle module split.

## Tier 2 (separate research session — do not implement here)

> **Update 2026-09:** the research is done (`docs/BEDROCK-RESOURCE-PACK-RESEARCH.md`) and the
> product direction is settled as "Java flagship + Bedrock guest"
> (`docs/BEDROCK-GUEST-MODE-PLAN.md`). That plan puts input feel and ball-flight smoothness
> ahead of the visual pack; the questions below remain the visual-parity checklist.

Visual parity for Bedrock, deferred. The research session should answer, against the pinned
Geyser 2.11.3 and current Bedrock tooling:

1. How does Geyser serve a Bedrock resource pack (config, pack hosting, per-server UUIDs),
   and can it convert/pass through a Java server resource pack?
2. Does this Geyser version support **custom blocks** (mapping Java `minecraft_golf:golf_*`
   to Bedrock blocks), and what does a `geyser_custom` block definition require?
3. Custom **items**: mapping the club items / `custom_data` to Bedrock models.
4. Custom **entities**: is there any supported path for the golf ball short of a mirrored
   vanilla entity, or is Bedrock stuck with the vanilla mirror?
5. Bedrock geometry/model format and the authoring tooling (Blockbench export, pack
   manifest/UUID, `RPACK` packaging) and how to version it with MC updates.
6. CI/packaging: how to build and ship the pack from this repo without breaking the Java
   resource layout.

Capture the findings in a new `docs/BEDROCK-RESOURCE-PACK-RESEARCH.md` before planning any
Tier 2 work.
