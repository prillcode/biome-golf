# M4.5 — Single-Player Loop Hardening: Closeout Record

Status: **Complete** on branch `m4.5-single-player-hardening`.

M4.5 hardens the configured single-player hole into a repeatable, understandable, and recoverable loop before multiplayer orchestration begins in M5.

## Delivered

| Area | Result |
|---|---|
| Lifecycle | Player-accessible start, restart, abandon, status, and Pick Up behavior. Start cannot silently replace an attempt; restart resets score and replaces the assigned ball; abandon returns the player to practice. |
| Practice separation | `[B]` uses a server-validated player practice-ball path. Practice balls are player-owned, are allowed only with no hole attempt, and are cleared for that player on start/restart. Operator `/golf spawn` remains an unrestricted unowned debug tool. |
| Recovery | Missing assigned balls are detected as an explicit recoverable state. Status and shot rejection direct the player to `/golf hole restart`; stale client state refreshes from authoritative server state. |
| Equipment | Starting a hole grants only missing clubs and does not duplicate the player's existing set. |
| Authoritative HUD | Typed server-to-client snapshots drive a client-only HUD showing hole/par, strokes/cap, penalties, score-to-par, active/missing/complete state, and final result. The client displays state but does not calculate outcomes. |
| Reconnect | Join/reconnect sends the current authoritative practice, active, missing-ball, or complete snapshot. |
| Safe terrain | Hole start rejects unloaded, submerged, or unsupported configured tee/cup positions with actionable configuration guidance instead of teleporting the player into unsafe terrain. |
| Development hole | `/golf dev preparehole` explicitly creates an idempotent bounded grass platform derived from the configured flat tee/cup. `scripts/dev-server-prepare-hole.sh` invokes it through Docker RCON and independently verifies key blocks. Normal startup does not rewrite terrain. |
| Development workflow | `dev-server/README.md` documents the hybrid Loom Singleplayer and authenticated Docker workflow, JAR synchronization/identity, preparation, restart/reset semantics, and manual integration checks. |

## Accepted behavior preserved

- Gameplay state, scoring, lifecycle decisions, and ball ownership remain server-authoritative.
- Common code under `src/main` contains no client imports.
- Practice shots remain available when no hole attempt exists.
- The player remains at the shot origin while the client-only camera follows the ball; automatic teleport-to-ball was not added.
- M4 cup-speed behavior, overspeed rejection, Putter tuning, penalties, Double Par + 2 cap, and terminal scoring remain intact.
- M5 multiplayer/Ready Golf and later course progression remain out of scope.

## Known limitations

- The product still supports one configured hole; multiplayer orchestration and multi-hole progression begin in M5 and M6 respectively.
- The prepared development-hole command intentionally supports flat tee/cup layouts and rejects sloped layouts rather than destructively flattening ambiguous terrain.
- Docker remains authenticated. Loom development identities must use Singleplayer or a temporary offline-only Loom server, not the tracked Docker server.
- Hole sessions are server-memory state rather than persistent global statistics; persistent statistics remain out of scope.

## M5 handoff

M5 can build Ready Golf multiplayer on the hardened contracts established here:

- explicit per-player lifecycle and ball ownership
- targeted cleanup that does not remove other players' balls
- server-authored hole-state snapshots
- client-only HUD presentation
- reconnect synchronization
- deterministic Docker practice environment and verification workflow

Do not replace these contracts with client-owned outcomes or global ball cleanup when adding multiplayer players.
